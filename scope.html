ThineCraft project scope

DriveCraft

Status: Early prototype. This document describes intended direction. A command-line client implementing part of it exists and passes automated tests against a stand-in server; it has had one manual trial against a small SharePoint Online test library and nothing larger. See Getting started for exactly what is and is not built.

Project website

Purpose

DriveCraft is the planned open-source OneDrive alternative for everyday synchronization, managed metadata, migration, and organization-controlled continuity across Linux, Windows, and macOS.

Confirmed direction

  • Desktop clients for Zorin OS and other Linux environments, Windows, and macOS.
  • A consistent view of files, sync state, versions, and managed metadata.
  • Rust as the implementation language, chosen for performance and for safe native integration with each operating system.
  • A desktop app built with Tauri: the core in Rust and the interface in HTML and CSS, shown in the operating system's own web view, with a system tray icon. The command line and the desktop app share one core and one catalog.
  • The desktop app runs on its own: it can start in the tray when the user signs in to the computer, only one copy runs at a time, and with automatic synchronization on it acts on local changes within seconds and checks the server once a minute. An ingest is only ever started by the user.
  • File Explorer integration (Windows): a library's folder can be registered with Windows as a sync root, the mechanism OneDrive uses. Windows then lists it in File Explorer under a name and icon chosen on this computer, and shows a status icon beside each item: in step with the library, or pending. DriveCraft keeps every file whole on disk and only tells Windows which items are in step; files on demand are not part of this. Check out and check in are offered in the right-click menu of files inside these folders. Everything is registered for the signed-in Windows user only, needs no administrator rights, and is undone by one switch. The status icons need the desktop app to be running.
  • Checked-out state: DriveCraft asks the server which files of a library are checked out, and by whom, after each synchronization, and keeps the answer in the catalog. The desktop app and the command line list them; the user's own can be checked in from the list, with a comment. In a folder shown in File Explorer the file carries a mark naming the holder. On very large libraries the server may refuse this question; DriveCraft then shows what it last knew, including every check-out made through DriveCraft itself.
  • Recycle bin, as built: the list is fetched once, newest deletions first, and kept while the app runs, so that finding something is immediate. Search and every filter run on this computer over what has arrived, including while older deletions are still being fetched. Listing and restore use the preview (beta) edition of Microsoft Graph, the only edition that offers them, with the permissions DriveCraft already asks for; Microsoft may change that edition without notice.
  • Browser Sync takeover, as built: one switch points the signed-in Windows user's handler for the Sync link at DriveCraft. It is exactly reversible: the previous setting is recorded before anything is changed, and switching off restores it value for value. DriveCraft never connects a library from a Sync press without the user confirming, can pass any single Sync press on to the program that had the button before, and does not remove, stop or reconfigure OneDrive. The record of the previous setting stays on the computer while DriveCraft has the button.
  • Library metadata (the columns a library defines for its files): people rarely use it because it is only reachable in the SharePoint web pages, so DriveCraft brings it to where they work. On Windows this is a details panel in DriveCraft, opened from a file's right-click menu, that shows a file's columns and lets the simple kinds be edited (text, number, yes/no, date, choice); it needs no administrator rights. Metadata as real, sortable columns in the file manager is not attempted on Windows: it would need a component installed by an administrator on every computer, and Windows gives the details of common file types to other programs. That is a goal for Zoron OS, where the file manager is ours to shape.
  • Installer, as built: a per-user Windows installer that needs no administrator rights and is distributed by us, not through a store. Removing DriveCraft undoes every change it made outside its own folders (the Sync button takeover, File Explorer registration and menu, starting with Windows) and leaves the user's files and DriveCraft's data in place. The installer is not yet code-signed.
  • Problems view: everything in a library that needs the user's attention is kept in the catalog and listed per library, in the desktop app and on the command line, with the reason and what to do. A problem that a run meets every time (a failed transfer, a refused name, a conflict, deletions held for confirmation, a run that stopped) is cleared by the next completed run that no longer meets it. A notice about something that happened once (a copy kept beside a changed file, a long path, a file kept after deletion in the library) stays until the user dismisses it or the file is gone. A preview records nothing.
  • On Windows, DriveCraft ships with its own installer and is not distributed through the Microsoft Store, so that the project keeps full control over how it installs, integrates with the system, and updates. The installer is built once the first release's features are complete.
  • A local SQLite catalog, embedded in the client, designed to track far more than 100,000 files. Removing the practical file-count ceiling of the OneDrive sync client is a primary goal.
  • A catalog that separates the description of the server (items, identifiers, hashes, change bookmark) from the state of the individual machine (what is downloaded, pending local changes).
  • A per-library seed: a read-only snapshot of the server part of the catalog, stored inside the document library it describes, so that additional machines can skip the first full scan. It is a starting point for initial synchronization only; afterwards each machine keeps itself current independently.
  • Check out and check in of files directly from the file manager's context menu, with the checked-out state visible on the file.
  • A configurable local folder name for each synchronized library, independent of the site or organization title, so that long titles such as "Trinidad and Tobago Securities and Exchange Ltd." do not have to appear in local paths.
  • A configurable icon for each synchronized library as shown in the file manager.
  • The local folder name and icon are chosen on each machine and stored only there; they are not distributed through the library or its seed.
  • A seed is published from a client on request, into a .drivecraft folder at the top of the library. A computer connecting to that library for the first time finds it without being told and starts from it. DriveCraft never synchronizes the .drivecraft folder as content.
  • A seed carries permissions, as built (decided by the project owner). DriveCraft learns which folders and files have permissions of their own from the change feed it already reads, and reads the permissions of only those items, twenty to a request, paced like every other request. When the person publishing is an owner of the library, and so sees everyone's permissions, the seed lists every item, restricted ones included, and for each restricted item who may open it: people, Microsoft 365 and security groups, SharePoint groups and sharing links, with their identifiers, names and e-mail or login where the server gives them, and what each may do. Anyone who can read the seed can therefore see the names and paths of restricted items and who may open them. When the person publishing is not an owner, the server shows them only the permissions that apply to them; DriveCraft says so at publish time and falls back to leaving each restricted item, and everything inside it, out of the seed, keeping only its identifier. An item whose permissions the server would not show is left out the same way. A catalog filled by an older DriveCraft reads the library's list once more, before its first seed, to learn which items are restricted.
  • A computer that starts from such a seed works out for its own user which restricted items they may not open, and removes those items and everything beneath them from its catalog, keeping only the item's identifier. The recorded permissions decide only where they are certain: they name the user, or a directory group the server says the user belongs to (read with the ordinary sign-in). SharePoint groups such as a site's Members or Visitors, sharing links, names known only to SharePoint such as "Everyone except external users", and groups the server would not list cannot be settled from the list; then the server is asked with the user's own sign-in, and nothing is kept on a guess. This produces no failures and no problems: one line in the log and a count in the run summary. A removed item is asked about again a day later, or as soon as the change feed mentions it, so access given later is picked up. A seed that lists no permissions (one made by a non-owner, or by an older DriveCraft) works as before: each left-out item is asked about with the user's own sign-in.
  • Items a user may not open never become failures. Whether or not a seed was used, a file the server refuses to hand over (or, for a file known only from a seed, says does not exist) is marked as not open to this user and skipped on later runs. The mark is dropped as soon as the server's change feed mentions the item again, for instance after the user is given access.
  • A permissions view, because SharePoint gives no single view of a library's permission structure. On the command line, drivecraft permissions NAME prints the library's own permissions, then each folder or file that has permissions of its own, indented under the folders that hold it, with who has what; --find searches by folder or file name and by person or group, and --refresh reads the permissions from the server again. In the desktop app the same is the Permissions dialog of a library, with a search box and filters for kind of person and kind of access. It works from the permissions recorded in the catalog, so it is instant on a very large library once they have been read. It is read-only: nothing can be changed from it. A person who is not an owner is told that the lists show only what applies to them.
  • Native ShareCraft integration.
  • Microsoft Graph integration for SharePoint and OneDrive discovery, migration, backup, and controlled synchronization.
  • Access to a user's personal OneDrive on their work or school account, in addition to shared SharePoint libraries.
  • Three operating modes, set for each connection between a local location and a library:
    • Sync: two-way synchronization between the local folder and the library.
    • Ingest: one-way migration from an existing disk source into the library. DriveCraft reads the source, including the files that symbolic links point to, and uploads; it never writes, changes, or deletes anything in the source.
    • Archive: one-way egress from the library to local storage. DriveCraft downloads only and never uploads or changes anything on the server. When a file is deleted on the server it is also removed from the archive; recovery of deleted files relies on the server's recycle bin.
  • Single sign-on with the Windows login: on a Windows machine signed in with a work account, DriveCraft uses that account without asking for credentials again. Other platforms and unmanaged machines fall back to signing in through the browser.
  • DriveCraft acts as the signed-in user. It can reach only the sites, libraries, and files that user is already permitted to reach; it does not hold organization-wide access of its own on the desktop.
  • Long path handling: DriveCraft warns when a file's path is too long for the local system or for the server. When Windows long path support is off, DriveCraft says so as a notice only. It does not change the setting or offer to; that decision belongs to the computer's administrator.
  • A recycle bin view in the client, showing what was deleted from a library and allowing it to be found and restored without using the SharePoint web interface. Finding something must be fast, because people look here when something is urgently missing: search by any part of the name, the folder or the person who deleted it, and filters for when it was deleted, by whom, the kind of file, and this library or the whole site. Several items can be restored at once. The second-stage recycle bin is out of scope: it needs an extra permission, and site administrators have the SharePoint web interface for it. DriveCraft never deletes from the bin or empties it.
  • The client respects server throttling: it honours the wait times the server asks for and backs off, rather than retrying aggressively or working around limits.
  • The client paces itself. It spaces its requests evenly, and when the server asks for a wait it cuts its pace, returns gently after the wait, and only later tests whether a faster pace is tolerated. The pace is learned from the server during each run; there is no setting.
  • When DriveCraft takes over from the Microsoft OneDrive client on a machine, it also takes over the "Sync" action in the SharePoint and OneDrive web pages, so that pressing Sync in the browser opens DriveCraft and adds that library.
  • Build order: DriveCraft works with OneDrive and SharePoint through Microsoft Graph first, so that people can try it against the files they already have and come to trust it; ShareCraft integration follows as ShareCraft takes shape.
  • Migration of files and metadata into ShareCraft or SharePoint.
  • An organization-wide offline copy on a server, NAS, or other privately controlled infrastructure.
  • Hybrid operation that combines cloud convenience with independent continuity and recovery.

Boundaries and non-goals

  • DriveCraft is not Windows-only and must treat Linux as a first-class platform.
  • It is not merely a backup utility; interactive synchronization, metadata, migration, and continuity are all core concerns.
  • It must support both ShareCraft-native environments and Microsoft 365 interoperability.
  • The offline copy is organization-controlled infrastructure, not an opaque vendor recovery tier.
  • Consumer OneDrive on personal Microsoft accounts is not supported; Microsoft 365 access is through work or school accounts only.
  • The desktop client does not embed or require PostgreSQL. A live catalog file is never shared between machines; only exported seeds are.
  • No implementation, benchmark, compatibility level, or production readiness is currently promised.

Expected integrations

  • ShareCraft document libraries, managed metadata, versions, permissions, and search.
  • Microsoft SharePoint and OneDrive through Microsoft Graph.
  • Local SQLite for durable file and metadata indexing on each client.
  • Servers, NAS devices, and private hosts for organization-wide offline copies.

Open decisions

  • Sync protocol, conflict handling, selective sync, placeholders, and offline semantics.
  • Filesystem integration and packaging strategy on each supported operating system, including installers and the web view dependency on Linux.
  • For the Windows installer: the installer technology, code signing, and how updates are delivered without a store.
  • Whether synchronization moves from the desktop app into a background service that runs without the window.
  • SQLite schema, indexing, change detection, and performance targets beyond 100,000 files.
  • Seed details still open: whether seeds are also refreshed automatically (today a seed is published only when someone asks for it).
  • What still has to be confirmed against a real tenant: whether the change feed marks items with permissions of their own when asked with Microsoft's hierarchicalsharing preference and DriveCraft's ordinary permissions (Microsoft says processing permissions correctly needs a permission that needs an administrator's consent, which DriveCraft does not ask for); whether an owner's permission lists are complete with those permissions; whether the group identifiers in permissions are the same as those the directory gives for a user's groups; and whether a refused item is answered as "not found" or "access denied" (both are handled). drivecraft permissions NAME --probe asks the server a few read-only questions and says what it answered, so this can be checked on a real library. If the change feed does not mark restricted items, a seed lists them as ordinary items without permissions; users still see no failures, because refused files are skipped quietly.
  • Whether items a user may not open are shown to that user at all (today they are not: they are removed from the catalog, counted in the run summary, and not listed in the problems view).
  • Whether a Microsoft Graph change bookmark created by one user can be used by another. It works for the same user on a second computer. If the server refuses a seed's bookmark, DriveCraft falls back to a full scan, so this decides speed, not correctness. Should the bookmark bring news of items the user may not open, they are skipped quietly: an item inside a left-out folder has no place to go and is ignored, and a file the server will not hand over is marked as not open to this user.
  • ShareCraft integration follows ShareCraft's own documented DriveCraft API (ShareCraft scope, SC-23), which does not claim Microsoft Graph compatibility. DriveCraft therefore has two connectors behind one internal boundary: Microsoft Graph, and the ShareCraft API. The ShareCraft connector waits on that API's design.
  • Database for the organization-wide offline copy; PostgreSQL is a candidate for that server-side component.
  • How context-menu actions, custom icons, and status indicators are delivered in each file manager (Windows Explorer, Linux file managers, macOS Finder), and what each platform permits.
  • How DriveCraft earns trust alongside the Microsoft OneDrive client: coexistence on the same machine, and whether a read-only or preview mode is offered before it is allowed to change files.
  • Taking over the browser Sync action: it relies on the link format Microsoft's web pages hand to the OneDrive client, which is undocumented and can change; and the OneDrive client may reclaim the action when it updates. How takeover is offered, kept, and handed back needs design.
  • Ingest details: handling of symbolic links that loop or point outside the source, whether a later run picks up only what changed in the source, and what happens to names and paths the server does not accept.
  • Archive details: whether earlier versions of files changed on the server are kept, and how the archive relates to the organization-wide offline copy.
  • Recycle bin details: how the view behaves on a bin with hundreds of thousands of items, and what to do if Microsoft changes or withdraws the preview interface it relies on.
  • Microsoft 365 sign-in and consent: the exact permissions requested, which of them an organization's administrator must approve once for the tenant, publisher verification for the ThineCraft app registration, and single sign-on equivalents on Linux and macOS.
  • How the organization-wide offline copy authenticates, since it runs without a signed-in user and would need access granted by an administrator.
  • Long path details: the thresholds that trigger a warning, whether the warning comes before or after a file is synchronized, and how to warn about programs that cannot open long paths.
  • Metadata mapping and fidelity between ShareCraft, SharePoint, local filesystems, and offline copies.
  • Encryption, key ownership, retention, recovery, and administrative policy.

Guidance for AI contributors

  1. Treat cross-platform support, managed metadata, Microsoft Graph interoperability, and the offline organizational copy as core scope.
  2. Do not describe planned behavior as implemented or tested.
  3. Do not reduce DriveCraft to a consumer sync folder or a backup-only product.
  4. Prefer portable data, transparent state, recoverability, and infrastructure the organization can control.
  5. Develop and test Microsoft 365 integration against a dedicated test tenant, never against an employer's or customer's production tenant.
  6. Record new product decisions in this file before presenting them as settled scope.
